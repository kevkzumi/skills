Implement the parent spec and its issue dependency graph on one **integration branch**. The coordinating author owns implementation, integration, fixes, and delivery. External Standards and Spec reviews inspect the complete integration only after all required issues are integrated.

This beta supports Codex and Claude Code coordinators. It requires Python 3.9+, Git, an authenticated opposite reviewer CLI, and a repo-backed installation. Resolve this skill's real directory through any symlink, then read the shared [handoff contract](../../../scripts/cross-review.md). Keep the complete fork checkout: its shared helper and existing review criteria are required. A copied skill folder is insufficient. Use this skill's `scripts/review.py` launcher for the commands below; it persists the required-parent-spec policy.

Where a harness lacks a literal Skill tool, read and apply the named model-invoked skill's `SKILL.md` through its available file tools. This fallback does not make user-only skills callable by another skill.

## Establish the task graph and baseline

1. Read the project's configured issue-tracker instructions before fetching the parent spec, its implementation issues, and blocking relationships. If no tracker is configured, tell the user to run `/setup-matt-pocock-skills`. Resolve missing issues, dependency cycles, and outside blockers before treating the graph as buildable. A missing parent spec blocks this workflow; Spec cannot be skipped.
2. Keep a local task graph with issue references, blockers, ownership, branches/worktrees, validation results, and integration status. An issue becomes **integrated** only when its implementation is on the integration branch and its relevant checks pass. Tracker closure is a later delivery action. The **frontier** contains issues whose blockers are integrated, or whose already-completed external dependencies have been verified. Start independent frontier issues concurrently within available agent capacity; queue the rest. With one available agent, assign implementer and merger roles sequentially, retaining issue worktree isolation and dependency checks. If subagents are unavailable entirely, report the capability blocker. If unfinished issues remain but the frontier is empty, report the dependency blocker and preserve work.
3. Fetch the full parent spec and relevant issue requirements into a temporary requirements file outside the project, retaining source references. Gather every applicable standards source, including ancestor instructions and their referenced documents. These files are the review inputs, not summaries of the latest issue. Communicate with subagents through these context pointers and existing artifacts.
4. Create an integration branch from the current branch, preserving its changes. Record the original integration baseline before new work starts. If requested implementation commits already exist, select an ancestor before those commits so review includes them. Preserve unrelated dirty work in place; use a clean integration worktree when necessary. Never reset, stash, or discard user work to obtain a clean start. Before author edits, run `begin` with the integration worktree, dedicated external session directory, `--baseline`, verified coordinating `--author`, and any user-requested `--reviewer-model`. Use explicit `--path` ownership for a dirty start or narrower scope. Resolve ownership conflicts before continuing.

## Build the frontier

5. Delegate each ready issue to an implementer subagent on its own branch and worktree based on the current integration tip. Give it the parent spec, issue, shared context pointers, owned files/responsibility, and validation expectations. Tell it that others are working concurrently and their changes must be preserved. Each implementer must:
   - Confirm the integration tip is an ancestor before starting; if its base is wrong, preserve existing work and create a correctly based worktree.
   - Call the Skill tool with "tdd" at appropriate, agreed seams and implement its assigned scope.
   - Merge the latest integration tip into its branch before reporting done, resolve conflicts, and rerun relevant validation.
   - Commit its issue implementation and report the commit, checks, remaining concerns, and recoverable work. Intermediate implementation and merge commits are allowed. Keep tracked issues unresolved for the coordinator's delivery gate.

   Implementers perform their assigned implementation only. They do not invoke either user-only implementation skill or automatically launch per-issue external reviews.
6. Use a merger subagent to merge each completed implementation into the integration branch. Serialize integration merges and confirm the implementer's branch includes the integration tip available at merge time; synchronize and revalidate if another issue landed meanwhile. Validate the combined state, record the issue as integrated, then recompute the frontier and start newly ready issues. If the configured tracker closes work through PRs, or the user requested one, create a draft PR after the first merge gives it work to propose. Keep it in draft, with the spec and issue references and any closing links required by the tracker, until the delivery gate passes.

## Review the complete integration

7. Once every required issue is integrated, reconcile the branch with the task graph and run the relevant integration checks and full relevant suite. Pause implementers, mergers, and author edits. Prepare final implementation commits before the final review when possible: a commit or merge after review changes the inspected revision and needs fresh review. Run `review` with the full requirements file and all standards sources, retaining the original session and baseline. The shared handoff supplies both reviewers one frozen scope covering every integrated issue plus owned staged, unstaged, and new files. Review the original integration range, never just the last merge or individual issue approvals.
8. Present Standards and Spec separately, with evidence, references, reviewer tool, requested model, and resolved model when known. The coordinating tool selects the opposite CLI through the shared handoff; use its criteria, restrictions, failure handling, and round counter without duplicating provider logic or substituting the native `code-review` dispatcher.
9. Assess every finding as the author. Delegate accepted fixes to one implementer when useful, commit and integrate the fixes, validate the combined implementation, and record the assessment using `assess`. Commit fixes before requesting fresh integration-wide review in the same session, so delivery needs no further source commit. Subsequent rounds inspect all issues and prior findings. At most three rounds are allowed, including failed or stale launched attempts. Unresolved disagreement, incomplete execution, or remaining material findings after round three blocks delivery; present the evidence and remaining work.

## Gate delivery and preserve work

10. Check that all required issues are integrated, validation passes, and `gate` returns `allowed: true` for the current integration state immediately before each delivery action. The helper checks the review state; the coordinator additionally checks graph completion and validation. If code, requirements, or integration state changed, stop delivery and follow the shared freshness rules. Reusing a passing per-issue review or beginning a replacement session cannot bypass a blocker.
11. On a blocker, keep the PR in draft, tracked work unresolved, integration branch intact, and all recoverable worktrees and review artifacts. Report the branch, integrated and pending issues, separate axis outcomes, rounds, findings, disagreements, validation, and the blocker. This is an incomplete run, not spec completion. Cleanup must not discard unfinished or unrelated work.
12. On success, follow the configured tracker completion workflow: mark the draft PR ready when PR merging resolves the work, or resolve the spec and issues through the configured direct workflow. A ready PR is not a merged PR; report its actual state. Report the integration branch, validation, separate review outcomes, reviewer identities, rounds completed, resolved and remaining findings, and any untested live behavior. If a delivery action fails, preserve the remaining work and report partial delivery accurately.
13. Clean up only completed implementer worktrees whose commits are reachable from the integration branch and whose tracked, untracked, and ignored files contain no recoverable work. Check for running agents first. Use ordinary `git worktree remove` without force; preserve any worktree that cannot be proven safe. Retain the integration branch and review artifacts. Report retained worktree paths and reasons.
